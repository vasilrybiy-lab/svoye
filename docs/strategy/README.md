## Як читати статуси

- **Є зараз / перевірено:** безпосередньо підтверджено поточними матеріалами сайту, робочими документами чи фактом здійсненої дії.
- **Узгоджений напрям:** стратегічне бажання/рішення розвивати, яке ще не обов'язково реалізовано.
- **Гіпотеза / потребує перевірки:** припущення щодо цінності, попиту або способу виконання.
- **Не є обіцянкою:** концепт, який не слід представляти клієнтам як запущену послугу.

1. **Поточний сайт у репозиторії**: [головна](../../app/page.tsx), [для батьків](../../app/parents/page.tsx), [підхід](../../app/approach/page.tsx), [про засновника](../../app/about/page.tsx), [малі проби](../../components/trial-experience.tsx).

3. **Напрацювання засновника й партнера (жовтень 2026)**: концепція екосистеми та «Своє Lab», ідея трьох рівнів участі, дослідницькі інтерв'ю з учасниками пілоту.
4. **Проєктні документи в репозиторії**: [MVP](../project-management/SVOYE_LAUNCH_PLAN_v1.0.md), [правила задач](../project-management/SVOYE_RULES_AND_TASKS_v1.0.md), [CRM](../CRM_ROADMAP_2026.md).

Якщо джерела не збігаються, не «виправляємо» їх непомітно: фіксуємо розбіжність у [журналі рішень](07-roadmap-and-decisions.md) й окремо затверджуємо зміну.

## Правила оновлень

1. Змінювати через GitHub pull request, бажано з позначкою **«Факт / Рішення / Гіпотеза»** й коротким поясненням.
2. Для стратегічної зміни оновити відповідні документи та рішення в [07](07-roadmap-and-decisions.md).
3. Для нової можливості сайту окремо перевірити фактичну реалізацію й не ставити «запущено» без тесту.
4. Переглядати roadmap щотижня на етапі запуску; позиціонування, продукти та Lab — щомісяця або після нового валідованого досвіду.
5. Не додавати у **публічний репозиторій** транскрипти дітей, імена/сімейні історії, приватні контакти, сирі нотатки, доступи, медичні/емоційні дані, цінові домовленості конкретних родин. Для досліджень вести окреме захищене сховище з правами доступу.

**Примітка:** ці документи описують стратегічне бачення; юридичні форми, фінансова модель, договірні умови й політика даних мають бути окремо перевірені перед запуском відповідних функцій.
