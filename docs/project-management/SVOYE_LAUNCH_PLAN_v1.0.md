## Оперативний план 3.4 — єдина чинна черга (14.10.2026)

> **Цей розділ є поточним статусом.** Нижчі історичні зрізи T01–T06 залишено як доказ минулих етапів, а не як поточні команди: публікація вже відбулася. Статус «реалізовано» ≠ «пройшло приймання».

## Головний пріоритет MVP — мінімальний час до запуску без критичних ризиків

**Рішення власника від 14.10.2026:** з цього моменту всі дії підпорядковані **якнайшвидшому запуску працюючого MVP**. Перед релізом закриваємо лише **критичні** наслідки; високі, середні, низькі тести та необов'язкову функціональність переносимо в vNext. [Головне правило R00 і тестове правило R11](./SVOYE_RULES_AND_TASKS_v1.0.md).

**Правило вибору дії:** якщо вона не усуває критичний ризик і без неї можна прийняти реальне бронювання, її відкладаємо. Після уже пройдених n8n synthetic #130–132 пріоритет — **не нові тестові копії**, а завершення головних неопублікованих чернеток та мінімальне критичне end-to-end приймання.

**Найкоротший критичний шлях:**
1. **T04:** після окремого дозволу внести мінімальні правки **неопублікованих** Telegram Assistant/Booking Engine: `claimed` → перевірена заявка Neon → виклик Engine, решта статусів → правдиві консервативні відповіді. [Готова специфікація змін](./T04_DRAFT_CHANGE_SPEC_2026-10-14.md).
2. **T05/T06:** з'єднати одноразове контрольоване створення Google/Meet з Neon finalize, заблокувати blind retry/false success; одна реальна контрольна подія **тільки після дозволу**.
3. **T08/T09:** мінімальний прямий перехід із сайту до Telegram, без додаткових екранів і функцій, що не потрібні першому запису.
4. **T10–T12:** один наскрізний критичний тест із перевіркою права доступу/приватності, достовірного повідомлення, ручного відновлення та способу вимкнути/відкотити. Далі **окреме рішення про публікацію і запуск**.

**Не блокує MVP:** T03 (штатні TTL/needs_review high), навантажувальні та повні матриці статусів, розширена дедуплікація алертів, додатковий UI, повтор уже успішних mock тестів без змін коду. **Але** якщо якась із цих поведінок створює критичний наслідок (дубль Google Create/фальшивий booked/розголошення даних), такий наслідок обов'язково усунути.

**Зміни в робочих системах:** нинішня пріоритизація сама по собі **не дозволяє** редагувати живі/опубліковані сценарії, публікувати n8n, викликати Google Calendar чи змінювати production Neon. Дозволи на редагування main draft, тестову реальну календарну подію та запуск — окремі контрольні рішення, але без додаткових погоджень для аналізу й документування.

## Оперативний статус — помилка Google Event GET виправлена (14.10.2026)

У реальних Engine executions **#137 і #145** три Calendar availability check пройшли (`available=true`), але Google Event Get для детермінованого ID повернув точний текст **`The resource you are requesting could not be found`** без числового `404`. ## 2. Підсумок T01 — звірка версій (read-only, 14.10.2026)

**Статус T01:** перевірено як аналітичну задачу; це **не** дозвіл на публікацію або доказ готовності бронювання.

Встановлено такі факти:

1. У Telegram Assistant додано 25 нових вузлів (перевірки календарів, збір власного контакту, callback-підтвердження, Neon, виклик Booking Request). Опублікована версія містить лише базовий AI-діалог із Telegram; також змінено параметри Telegram Trigger і системне повідомлення AI Assistant.
2. У чернетці Telegram підтвердження з гілки `Booking Claimed?` йде до `Booking Reserved — Test.` та тестової відповіді. Прямого виклику `Booking Engine` з цього маршруту не встановлено. Не можна говорити клієнту про завершене бронювання.
3. У Booking Engine додано 24 нових вузли (перевірка claim, стани Neon, обробка `needs_review`, завершення запису). Але `Create an event` вимкнено **і** в поточній чернетці до нього немає вхідного з'єднання від `Calendar Create Granted?`. Також `Find Existing Booking Event — Google` не має вхідного з'єднання; вузол `Existing Event Not Found?` має незаповнену умову. Шлях від початку до `Finalize Booking — Neon` через створення події не працює в поточній граф-схемі.
4. У тестовому Engine Google Calendar-вузли вимкнені, замінені MOCK-вузлами та використовується окремий тестовий PostgreSQL credential. Історичні виконання 124–127 пройшли відповідні mock-сценарії: успіх, зайнятість, невизначена доступність та невідомий результат створення. **Поточний** `TEST — Manual Trigger` спрямований лише до `TEST — Safety Stop`, тоді як `TEST — Scenario Input` має окремий маршрут: спосіб безпечного повторного запуску тестів потрібно уточнити до нових виконань.
5. Booking Request має тестовий допуск і маршрут `Insert Booking — Neon → Request Phone — Telegram`, однак не має опублікованої версії. Взаємодію з майбутньою опублікованою версією AI потрібно перевірити окремо.

**Головний ризик:** намагатися опублікувати всі чернетки без виправлення викликів і маршруту календаря. Це може дати підтвердження, яке не відповідає реальному створенню зустрічі, або неповну обробку невизначеного результату.

## Правило відбору тестів до MVP — лише критичні

**Уточнення власника від 14.10.2026:** до MVP виконувати **тільки критичні тести**. Усі **високі, середні та низькі** — у наступну версію (vNext). Відкладений тест не є PASS. Рівень ризику визначаємо за **наслідком**, а не за назвою технічного сценарію. Якщо звичайна помилка TTL або зайнятості призводить до подвійного Google Create чи хибного підтвердження — перевіряємо саме цей критичний наслідок до запуску. T03 high-ризиків лишається у vNext.

**Прогноз:** попередній базовий діапазон 31–60 годин ще не перераховано: тест DB не дорівнює інтеграції Telegram/Google. Відсоток готовності MVP залишається невизначеним.

## 6. Правила актуалізації

Після завершення суттєвого етапу оновлюємо цей план (чергу, оцінку, прогноз, блокери) і постійний реєстр задач (статус/доказ). Сутнісні правила в регламенті не змінюємо без домовленості. Ризикові операції — тільки за погодженням. Діє правило двох спроб та пошуку альтернатив.
