# T02 — перевірка повторів і конфліктів бронювань

**Дата:** 14.10.2026  
**Статус:** частково перевірено; **T02 залишається в роботі**  
**Середовище:** Neon project `svoyechat-test`, гілка `test/booking-engine-v1` (ID `br-delicate-heart-b7h6nwzw`); n8n / Google API **не запускалися**.  
**Підхід:** прочитано визначення функцій PostgreSQL, обмеження та індекси; проведено цільові виклики тестових DB-функцій на завчасно створених синтетичних fixtures; перевірено стан після викликів. Жодної DDL, публікації, операції Google чи запису в production не виконано.

## 1. Перевірені результати

| № | Вхідна умова | Очікувано | Фактично | Висновок |
|---|---|---|---|---|
| 1 | Повторне підтвердження вже `booked` | `already_booked` | `already_booked` | PASS |
| 2 | Інший Telegram-користувач на `pending` | `unauthorized` | `unauthorized` | PASS |
| 3 | Повторна спроба підтвердити `needs_review` | `already_needs_review` | `already_needs_review` | PASS |
| 4 | Повторний `svoye_finalize_booking` із тим самим event ID | `already_booked` | `already_booked` | PASS |
| 5 | Повторний `svoye_mark_booking_review` | `already_needs_review` | `already_needs_review` | PASS |
| 6 | `pending` на час, зайнятий іншим `booked` | `slot_unavailable` | `slot_unavailable` | PASS |
| 7 | Та сама колізія, друга спроба | `slot_unavailable` | `slot_unavailable` | PASS |

Обмеження `slot_no_overlaps` (GiST, `tstzrange(...,'[)')`) забороняє перетин для слотів зі статусами `held`, `booked`, `needs_review`. `svoye_claim_booking` блокує рядок заявки через `FOR UPDATE`, а конфлікт вставляння слота перетворює на `slot_unavailable`. Це статична перевірка механізмів + послідовні функціональні тести, **а не доказ поведінки під реальною одночасністю**.

## 2. Стан тестової БД після перевірок

- Конкуруюча заявка: `pending` (без змін).
- Кількість слотів для неї: `0`.
- Активні `held`: `0`.
- Перетинів активних слотів: `0`.
- Неузгоджених пар `booking_requests / booking_slots`: `0`.
- `booked`: `2`; `needs_review`: `3` (кількості тестових fixtures, **не** реальних зустрічей).

Стан підтверджено окремим read-only запитом одразу після тестів.

## 3. Що залишається до завершення T02

1. **Дві одночасні незалежні транзакції:** створити ізольовані синтетичні `pending` fixtures, зробити одночасний claim на один слот, перевірити один `claimed` і один `slot_unavailable` (або коректно оброблений lock timeout), відсутність дублювання.
2. **Double-click Telegram callback:** імітувати два однакові callback та повтор виконання після таймауту на тестовій n8n-гілці; очікувати один результат claim і відсутність повторної Google-операції.
3. **Hold expiry / cleanup:** перевірити, що прострочений hold звільняється лише за дозволених станів, а `needs_review` ніколи не втрачає блокування слота без ручної перевірки.
4. **Безпечний вхід до n8n TEST:** поточний `TEST — Manual Trigger` підключений до `TEST — Safety Stop`; будь-яку зміну тестового маршруту погодити окремо, зберігши заборону на Google API й прив'язку лише до Neon TEST.
5. **Окремі контрольні початкові та кінцеві стани** для кожного сценарію; не використовувати production-контакти й токени.

## 4. Обмеження висновків

- Послідовна колізія тестує DB exclusion, але не конкурентні блокування/таймінги.
- `Booking Engine TEST` під час цього етапу **не виконувався**; попередні mock-успіхи описані в окремих попередніх звітах.
- Під час цього етапу **не створено** жодного реального Calendar event / Meet.
- Статус `T02`: **У роботі** до зазначених concurrency/callback/TTL тестів.

## 5. Наступний крок

Підготувати безпечний сценарій конкурентного тесту з двома ізольованими транзакціями та контрольованим створенням **лише синтетичних** fixtures у тестовій Neon. Зберігати `TEST — Safety Stop`, доки не узгоджено необхідний спосіб запуску. Перед тестовими записами уточнити дозвіл на підготовку/очищення fixtures (не торкатися production).
