# «Своє» · Сайт B → Telegram: контракт безпечної передачі контексту

**Статус 14.10.2026:** код сайту B додано, однак **інтеграція не активна**. Не змінювати живий Telegram-бот під час тесту відкладених нагадувань і двох окремих чатів. Сайт A (`main`) недоторканий.

## Суть та межі

Після проходження однієї малої проби та трьох блоків рефлексії відвідувач бачить власний повний підсумок, може його скопіювати й **за явною згодою** підготувати передачу AI-асистенту «Своє» в Telegram.

*Сайт не відкриває Telegram як заміну конфіденційній передачі.* URL міститиме **тільки одноразовий випадковий код**; відповіді, ім’я й номер телефону в URL не потрапляють. Копіювання тексту і реальна доставка в бот — різні речі.

### Реалізована частина B

- Клієнтська сторінка: `components/mobile-journey-home.tsx` і `app/mobile-journey.css`. Вивід повного тексту в `details`; окремий opt-in checkbox; асинхронне створення посилання після згоди; окрема явна дія «Відкрити Telegram»; безпечне копіювання як fallback.
- Сервер Next.js `app/api/website-handoff/route.ts` (`runtime=nodejs`). `GET` повертає `{enabled:false}` доки весь ланцюг не ввімкнений. `POST` — same-origin JSON, згодa `true`, `contextVersion:1`, довжина тексту 1–4000 символів, тіло до 9 KB.
- **Fail closed**: `SVOYE_HANDOFF_BOT_READY` must equal `true`, а `SVOYE_HANDOFF_WEBHOOK_URL` та `SVOYE_HANDOFF_WEBHOOK_SECRET` мають бути задані як **server-only** Vercel env vars. Відсутність бодай одного — 503, посилання не створюється. `NEXT_PUBLIC_*` тут не використовувати.
- Webhook-адреса допускається лише HTTPS під `*.n8n.cloud`. Сайт сам створює криптографічний випадковий token 32 bytes у base64url (43 символи) і зберігає на боці сервера **лише SHA-256** від token. Raw token не надсилається webhook/DB.
- Завершене збереження webhook повинен підтвердити `{"stored":true}`. Без позитивної відповіді жодного URL.
- Успіх: сайт повертає URL `https://t.me/jerryforvasylbot?start=sv_<43-base64url>`, TTL 10 хвилин. Client не вміщує текст у параметри deep link.
- Поки env vars відсутні, відвідувач бачить повідомлення «ще налаштовуємо» і копіювання — без кнопки, яка лише видає помилку.

## Наступний крок у n8n — окремий, не для живого бронювання

1. Створити **ізольований POST webhook для отримання підсумку**. Відхиляти запити без `Authorization: Bearer <secret>`. Ніколи не показувати секрет у логах чи фронтенді. Налаштувати IP/rate limit на рівні сервера/webhook/Cloudflare/Turnstile до відкриття публічного API; same-origin сам собою не зупиняє бота, що імітує браузер.
2. Перевіряти source `svoye_website`, `context_version=1`, `message_text` (1–4000), `token_hash` (64 lowercase hex), `expires_at` (майбутнє, максимум 10 хв). SQL parameters ONLY, ніяких динамічних рядків із тексту. Зберегти в **існуючу** `public.website_requests`:
   `source, message_text, token_hash, expires_at`. Обмежити повторні заявки на користувача/IP й загальний rate; строк зберігання та видалення прострочених текстів — узгодити в політиці даних.
3. Тільки після перевірки цього endpoint він може відповідати `{"stored":true}`. Завдання зберігати одне звернення і створювати один код. Працювати спочатку в тестовій Neon branch і НЕ змінювати наявні бронювання/слоти.
4. У головному Telegram-боті додати новий маршрут **`/start sv_<43-base64url>` перед загальним AI Text Message**. Інші `/start` залишити без змін. Секрети не передавати на стороні Telegram.
5. По отриманню deep link, валідувати Telegram `message.from.id` і `message.chat.id` (приватний діалог; не прив’язувати до owner/admin). Порахувати SHA-256 **від сирого token**. Атомарно й *рівно один раз* погасити код:
   ```sql
   UPDATE public.website_requests
      SET telegram_user_id = $2::bigint,
          claimed_at = now()
    WHERE token_hash = $1::text
      AND telegram_user_id IS NULL
      AND claimed_at IS NULL
      AND expires_at > now()
    RETURNING id, message_text;
   ```
   Якщо `RETURNING` порожній — відповісти «Посилання прострочене або вже використане» без викриття даних і без повторного імпорту. Це забезпечує одноразовість, якщо транзакційні гарантії Neon зберігаються.
6. Для успішного claim — **спочатку повідомити клієнту** «Отримав твій підсумок із проби…», а потім передати `message_text` в AI як *дані користувача*, не як system/developer instructions. Враховувати пам’ять відповідного Telegram chat ID, але не перемішувати чати.
7. **Не проводити безпосередній booking із сайту**, не обходити існуюче підтвердження номера й календарні атомарні перевірки. /call доступний лише власнику; бронювання лишається окремим маршрутом, тестові allowlists без змін.
8. Після наскрізного тесту з двома акаунтами й перевірки privacy встановити три env vars в **окремому Vercel проєкті B**. Тільки тоді `GET /api/website-handoff` зміниться на `enabled:true`.

### Server → webhook request (тільки всередині)

```json
{
  "source": "svoye_website",
  "context_version": 1,
  "message_text": "Моя мала проба...",
  "token_hash": "64 hex chars",
  "expires_at": "2026-10-14T13:00:00.000Z"
}
```

- HTTP `POST` під HTTPS; `Authorization: Bearer <secret>`. JSON; 8s timeout.
- Відповідь: HTTP 200 JSON `{"stored":true}` після **успішного** INSERT; будь-яка інша відповідь = fail closed, клієнту пропонується копіювання.
- `GET /api/website-handoff` status не містить жодних секретів.

## Тести до активації

- Кожен із дев’яти сценаріїв: коректний підсумок, `null` для «цього не було», пропуск труднощів, нотатки з кирилицею.
- Без opt-in відправлення **неможливе**, після зміни відповідей попередній handoff URL у UI скидається.
- До env activation: `GET enabled:false`, `POST 503`, `website_requests` не змінюється.
- При увімкненні: тільки один активний код, токен не зберігається в DB, код не містить відповіді, claim success → правильний окремий чат; другий claim/expiry/invalid token → відмова; випадкова інша особа із токеном може отримати контекст — тому код є bearer-credential, не ділитися ним та TTL має бути малим.
- Чітка політика очищення старих текстів, не віддавати raw answers у сторонні analytics/server logs; конфіденційність і згода для підлітків.
- Після deploy перевірити build і реальну роботу на мобільному, в тому числі невисокі дисплеї та back-navigation.

**Операційний пріоритет:** завершити тест автоматичних нагадувань чинного Telegram booking на 15.10.2026, потім під’єднати новий н8n webhook і redemption handler, потім env у Vercel B, потім E2E; не публікувати зміну ролей на боті під час активної перевірки.
